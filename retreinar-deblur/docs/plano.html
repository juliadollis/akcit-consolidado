As mudanças

C1

proj_out de topo está recebendo LoRA

bloqueante

genfocus_train/backbone.py:83 · idêntico nas duas árvores

Como está

LORA_TARGET_MODULES = [
    "to_q", "to_k", "to_v", "to_out.0",
    "norm1.linear",
    "ff.net.2",
    "norm.linear",
    "proj_mlp",
    "proj_out",        # ← linha 83
    "x_embedder",
]

Por que é problema

PEFT casa alvo por key == target or key.endswith("." + target). A projeção final do FluxTransformer2DModel chama-se literalmente proj_out no topo do módulo, então além dos 38 single_transformer_blocks.N.proj_out o PEFT injeta LoRA também em transformer.proj_out.

Essa camada é executada sem controle por branch:

image_hidden_states = self.norm_out(all_hidden_states[txt_n], tembs[txt_n])
output = self.proj_out(image_hidden_states)      # ← FORA de qualquer specify_lora

Sem specify_lora, o scaling fica no valor natural (alpha/r = 1) e a LoRA age incondicionalmente, inclusive com main_adapter=None. Duas consequências: a variante _paper não é “LoRA só na condição”, e a entrada dessa camada depende do temb do main — que é onde o descasamento de guidance do C2 entra mesmo no cond-only.

Prova por contagem, contra o header do bokehNet.safetensors oficial já dumpado (686 tensores, 343 módulos):

GrupoMódulos por blocoBlocosTotal
Duplosto_q, to_k, to_v, to_out.0, norm1.linear, ff.net.219114
Singleto_q, to_k, to_v, norm.linear, proj_mlp, proj_out38228
Topox_embedder11
Oficial343
Topo (extra)proj_out11
Nosso344

Conferido que não há outros falsos positivos: norm_out.linear, norm1_context.linear, ff_context.net.2, add_q_proj e to_add_out não casam com nenhum alvo.

Como tem que ficar

Trocar as strings soltas por regex ancorado nos blocos. LoraConfig aceita target_modules como str e, nesse caso, PEFT usa re.fullmatch — por isso as âncoras são obrigatórias.

# Alvos ancorados nos BLOCOS. Strings soltas não servem: PEFT casa por
# `key == target or key.endswith("." + target)`, e a projeção final do
# FluxTransformer2DModel chama-se `proj_out` no topo do módulo — ela seria
# capturada e ficaria ativa FORA do controle por branch do specify_lora.
LORA_TARGET_MODULES = (
    r"^(transformer_blocks|single_transformer_blocks)\.\d+\."
    r"(attn\.(to_q|to_k|to_v|to_out\.0)|norm1\.linear|ff\.net\.2|"
    r"norm\.linear|proj_mlp|proj_out)$"
    r"|^x_embedder$"
)

E uma trava dura em _inject_lora(), logo depois do add_adapter:

from peft.tuners.lora import LoraLayer

if len(lora_modules) != 343:
    raise RuntimeError(
        f"LoRA injetado em {len(lora_modules)} módulos; o oficial tem 343. "
        f"Módulos de topo (suspeitos): {[n for n in lora_modules if '.' not in n]}"
    )
Migração — obrigatório ler

Depois desta mudança, maybe_resume_checkpoint encontra proj_out.lora_A.default.weight no checkpoint antigo, classifica como unexpected e só imprime um WARN, descartando o peso em silêncio. Isso muda o modelo sem avisar.

Treinos novos começam do zero. E o WARN vira erro:

Guidance do treino não bate com a inferência do Deblur

alto

Como está

Por que é problema

A inferência oficial usa valores diferentes por estágio. O default é guidance_scale: float = 3.5 (flux.py:467), e flux.py:707 monta guidances = [guidance]*2 + c_guidances:

Os autores baixaram de propósito a guidance no BokehNet e deixaram 3,5 no DeblurNet — duas fontes independentes confirmam. A auditoria em historico-ultimo.md:283 registra “Guidance: todas 1.0 — confere com a inferência de bokeh”. Está certa para o BokehNet; a conclusão foi carregada para o DeblurNet sem reconferir.

A guidance entra só via get_temb, que produz o vetor de modulação daquele branch. A severidade depende de quais módulos LoRA consomem esse temb:

VarianteQuem consome o temb do mainSeveridade
cond-only pós-C1nenhum LoRA no mainindireta, leve
cond-only hojeproj_out de topo, sobre o hidden state do mainmoderada
main+condnorm1.linear (19) e norm.linear (38) recebem o temb como entrada diretasevera — é o modelo de 60k

Como tem que ficar

Parar de hardcodar. Em ModelConfig:

# Guidance embutido no temb de cada branch. NÃO é CFG — o FLUX.1-dev é
# guidance-distilled e recebe esse escalar como entrada do modelo.
# Tem que ser o MESMO da inferência do estágio:
#   deblur: Inference_deblurNet.py não passa guidance_scale -> default 3.5
#   bokeh:  Inference_bokehNet.py passa guidance_scale=1.0
# A condição recebe 1.0 nos dois casos (flux.py:622).
deblur_train_guidance: float = 3.5
bokeh_train_guidance: float = 1.0
cond_train_guidance: float = 1.0
guidance_main = torch.full((B,), self.train_guidance, device=device, dtype=dtype)
guidance_cond = torch.full((B,), self.cond_guidance, device=device, dtype=dtype)

Gravar o valor usado no metadata do checkpoint (C8).

Medir antes de retreinar

O modelo de 60k já existe. Rodar a avaliação em akcit-pixel/DDPD:test com guidance_scale ∈ {1.0, 3.5} passado explicitamente, resto idêntico. Se 1,0 ganhar, o treino está certo e é a inferência que precisa passar guidance_scale=1.0 — corrija os scripts e documente o desvio. Se 3,5 ganhar, confirma que o treino é que estava errado. C3

O primeiro update roda com LR 500× maior que o previsto

alto

genfocus_train/trainer.py:686-688 · nas duas árvores

Como está

if accelerator.sync_gradients:
    ...
    optimizer.step()                     # ← usa o LR que estiver no param_group
    optimizer.zero_grad(set_to_none=True)

if accelerator.sync_gradients:
    state.global_step += 1
    scheduler.step(state.global_step)    # ← só AGORA o LR é ajustado

Por que é problema

O param_group["lr"] nasce com config.optimizer.lr (1e-4) e o scheduler só é aplicado depois do primeiro optimizer.step(). Além disso o índice fica deslocado: global_step já foi incrementado e _lr_at usa (step + 1) / warmup. Executando o scheduler isolado com lr=1e-4, warmup=500:

UpdateRealCorreto
#11.000e-042.000e-07
#24.000e-074.000e-07
#36.000e-076.000e-07
#48.000e-078.000e-07

O primeiro update aplica LR 500× acima do início do warmup, sobre pesos LoRA recém-inicializados — exatamente o update em que o warmup existe para proteger. Depois disso o warmup inteiro roda um step adiantado.

Como tem que ficar

Duas mudanças, ambas necessárias. Primeiro, aplicar o LR antes do primeiro update — depois do maybe_resume_checkpoint e antes de iterator = _cycle(dataloader):

# O param_group nasce com o lr base; sem isto o PRIMEIRO update roda com
# 1e-4 em vez do primeiro passo do warmup. No resume, reposiciona o LR no
# ponto certo da curva.
scheduler.step(state.global_step)

Segundo, corrigir o deslocamento em WarmupCosineScheduler._lr_at:

def _lr_at(self, base_lr: float, step: int) -> float:
    if step < self.warmup_steps:
        # step é 0-based e representa quantos updates JÁ ocorreram.
        # max(step, 1) evita LR exatamente 0 no primeiro update.
        return base_lr * float(max(step, 1)) / float(max(1, self.warmup_steps))
    ...

Verificar: no wandb, deblur/lr no step 10 tem que ser 2.0e-06, e 1.0e-04 nunca deve aparecer antes do step 500.

C4

Escala espacial × cronograma de sigma

alto · decisão medida

genfocus_train/data.py:144-200 · genfocus_train/backbone.py:301-325, 364

Como está

scale = image_size / min(w, h)          # data.py:166 — lado MENOR vai para 512
new_w = max(image_size, round(w * scale))
new_h = max(image_size, round(h * scale))
...
sigma_u = self.sample_sigma(B, N, device, dtype)   # backbone.py:364 — N = 1024 (o crop)

Por que é problema

Dois eixos precisam bater entre treino e inferência, e hoje nenhum regime acerta os dois. Números com a config do FLUX-dev (base_seq=256, max_seq=4096, base_shift=0.5, max_shift=1.15), assumindo armazenado 1024×688:

RegimeDims por forwardseqmuexp(mu)Escala vs treino
treino512×51210240,63001,8781,000×
eval long_side=512512×3366720,57041,7690,672×
eval long_side=0tile 512×51210240,92252,5161,344×

O mu do long_side=0 vem de 2752 tokens da imagem inteira, não dos 1024 do tile.

long_side=512 erra a escala espacial: o treino reduz o lado menor e a avaliação reduz o lado maior, então o blur na avaliação é 1,49× menor do que o modelo viu. long_side=0 acerta melhor a escala e o seq do forward — o tile é 32×32 tokens = 1024, igual ao treino — mas erra o cronograma de sigma: em flux.py:624, image_seq_len = latents.shape[1] é da imagem inteira, calculado antes do tiling.

Como tem que ficar

Existe uma opção que acerta os dois eixos, e é a que corresponde ao regime que os autores assumem — demo.py:298: “Disable tiling tricks: Not recommended when the longer side is around 1000px or more”, ou seja, imagem grande com tiles de 512×512 px nativos.

Opção A (recomendada) · crop nativo + mu da imagem inteira

1. Em prepare_aligned_pair, não redimensionar. Só fazer upscale se algum lado for menor que 512:

w, h = aif_pil.size
if min(w, h) < image_size:                      # única situação que exige resize
    scale = image_size / min(w, h)
    new_w, new_h = round(w * scale), round(h * scale)
    aif_r  = aif_pil.resize((new_w, new_h), Image.BICUBIC)
    blur_r = blur_pil.resize((new_w, new_h), Image.BICUBIC)
else:
    new_w, new_h = w, h                          # ESCALA NATIVA: o crop 512x512 é
    aif_r, blur_r = aif_pil, blur_pil            # o mesmo tile que a inferência vê

2. O dataloader devolve o seq_len da imagem de origem inteira:

fw, fh = (new_w // 16) * 16, (new_h // 16) * 16
full_seq_len = (fw // 16) * (fh // 16)          # ex.: 1024x688 -> 64*43 = 2752

3. sample_sigma passa a aceitar seq_len por amostra:

def sample_sigma(self, seq_len: torch.Tensor, device, dtype) -> torch.Tensor:
    """seq_len: (B,) — tokens da IMAGEM DE ORIGEM inteira, não do crop.
    A inferência oficial calcula mu de latents.shape[1] da imagem completa
    (flux.py:624), ANTES do tiling; cada tile herda esse cronograma."""
    B = seq_len.shape[0]
    u = torch.sigmoid(torch.randn(B, device=device, dtype=torch.float32))
    cfg = self._scheduler_config
    m = (cfg.max_shift - cfg.base_shift) / (cfg.max_image_seq_len - cfg.base_image_seq_len)
    mu = seq_len.to(torch.float32) * m + (cfg.base_shift - cfg.base_image_seq_len * m)
    exp_mu = torch.exp(mu)
    sigma = (exp_mu * u) / (1.0 + (exp_mu - 1.0) * u)
    return sigma.to(dtype=dtype)

4. Avaliar sempre com long_side=0 e tiling ligado, e remover long_side=512 de scripts/make_examples.py:80.

Opção B (alternativa) · tudo a 512², sem tiling

Treinar reduzindo o lado maior para 512 (imagem inteira, não crop) e avaliar com long_side=512 e NO_TILED_DENOISE=True. Acerta os dois eixos também, mas abandona o regime nativo dos autores e perde detalhe fino.

O experimento que decide

Não escolha por argumento. Três treinos de ~3000 steps, mesma seed, mesmos dados, já com C1+C3:

RunDataloadermu do sigma
R1 (atual)lado menor → 512, crop 512²do crop (1024)
R2 (Opção A)crop nativo 512²da imagem inteira
R3 (Opção B)lado maior → 512, imagem inteirado próprio 512²

Avaliar os três em DDPD:test nos três regimes de inferência e montar a matriz 3×3 de LPIPS/DISTS. Reportar a matriz inteira, não só a diagonal — o objetivo é saber se algum run é robusto fora do próprio regime.

top_k_sharpest seleciona linhas, não cenas

médio

genfocus_train/data.py:401-463

Como está

for i, row in enumerate(dataset.select_columns([column])):
    scores[i] = _laplacian_variance(row[column])     # column = "image_focus"
top_idx = np.argsort(scores)[::-1][:k]               # data.py:442 — ranking por LINHA

Por que é problema

akcit-pixel/RealBokeh:train tem 20.495 linhas para ~3.960 cenas: cada linha é (uma entrada borrada de abertura X, o mesmo image_focus f/22 da cena). Como o score é medido em image_focus, ele é idêntico dentro da cena — os empates são exatos. O argsort puxa cenas inteiras, e o top-3000 vira ~580 GTs distintas repetidas ~5,2×.

O paper é explícito em §B.1 — “we retain the top 3,000 sharpest images” — e §4.1 fecha em 3,5K pares (344 DPDD + 3000 RealBokeh). Não é um desastre, mesmo alvo com blurs diferentes é boa aumentação, mas é 5× menos diversidade de conteúdo do que o número sugere.

Como tem que ficar

Ranquear por cena e amostrar a linha dentro da cena. Preserva os 3000 pares do paper, recupera a diversidade e mantém a aumentação por abertura.

1. Identidade da cena — medir primeiro qual chave existe (C0-2). Preferir, nesta ordem: coluna explícita de cena; prefixo de file_name_base; hash dos bytes de image_focus.

def _scene_key(record: dict) -> str:
    """Identidade da CENA. O ranking de nitidez tem que ser por cena, não por
    linha: no RealBokeh o mesmo image_focus f/22 aparece em ~5 linhas (uma por
    abertura), com score de Laplaciano idêntico, e o top-k puxaria cenas
    inteiras (~580 GTs para 3000 linhas) em vez de 3000 imagens distintas."""

2. Novo seletor: agrupa índices por cena, mede a variância uma vez por cena, ranqueia cenas, pega as top-k, devolve os grupos.

3. HuggingFaceDeblurDataset passa a ter __len__ == k e sorteia a linha:

    row_i = grupo[0] if not self.runtime.train else int(self._rng.integers(len(grupo)))
    record = self.dataset[row_i]

Versão mínima, se a acima for muito invasiva: deduplicar para uma linha por cena (a de maior blur) antes de medir, e então ranquear. Perde a aumentação por abertura.

C6

A inferência do main+cond liga LoRA no branch de texto

médio

scripts/infer_mainlora.py · vision-pipeline/inference/src/pipelines/deblur_net.py

Como está

Passa-se main_adapter="deblurring" para compensar o treino main+cond.

Por que é problema

generate monta adapters = [main_adapter] * 2 + c_adapters, e o índice 0 é o branch de texto (txt_n = 1). No single_block_forward os hidden states são [*text, *image] e o texto passa por:

with specify_lora((self.norm.linear, self.proj_mlp), adapters[i]):   # i = 0 -> texto
with specify_lora((self.proj_out,), adapters[i]):

Ou seja, main_adapter="deblurring" liga LoRA no texto em 38 blocos single. Mas o treino original (genrefocus_deblurnet/genfocus_train/backbone.py:407) usa [None, ADAPTER_NAME] + [ADAPTER_NAME] * n_cond — texto sem adapter. Nos blocos duplos não há efeito: os módulos do texto não são alvos de LoRA nem passam por specify_lora.

Como tem que ficar

Não tocar em third_party/Genfocus/ — é o clone de referência. Adicionar o parâmetro na nossa cópia, vision-pipeline/inference/Genfocus/pipeline/flux.py:

def generate(
    ...,
    main_adapter: Optional[List[str]] = None,
    text_adapter: Optional[str] = "__same_as_main__",   # DESVIO NOSSO, ver nota
    ...
):
    # NOTA (desvio deliberado do upstream): o generate oficial monta
    # `adapters = [main_adapter]*2 + c_adapters`, e o índice 0 é o branch de
    # TEXTO. Nosso DeblurNet main+cond foi treinado com [texto=None,
    # main=LoRA, cond=LoRA]; passar main_adapter="deblurring" ligaria LoRA no
    # texto em 38 single blocks, coisa que o treino nunca fez.
    _text = main_adapter if text_adapter == "__same_as_main__" else text_adapter

Substituir [main_adapter] * 2 por [_text, main_adapter] nas três chamadas a transformer_forward — ramo tiled, ramo normal e ramo image_guidance_scale != 1.0. Nos scripts do modelo main+cond, passar main_adapter="deblurring", text_adapter=None.

Verificar: avaliar o mesmo peso de 60k nas duas configurações em DDPD:test. Se a diferença for desprezível, documentar e seguir; se não, as métricas anteriores precisam ser refeitas.

C7

Todos os ranks sorteiam o mesmo ruído e o mesmo sigma

baixo

genfocus_train/trainer.py:549

Como está

_set_seed(config.runtime.seed)      # idêntico em todos os processos

Por que é problema

Com 4 GPUs × gradient_accumulation_steps=8, o batch efetivo é 32 — mas os 4 ranks sorteiam os mesmos 8 sigmas e os mesmos 8 tensores de ruído. O batch tem só 8 σ distintos em vez de 32, o que aumenta a variância do gradiente sem nenhum ganho. Os pesos LoRA continuam idênticos entre ranks porque há broadcast explícito do rank 0, então diferenciar a seed é seguro.

Como tem que ficar

accelerator = _build_accelerator(config)
# Seed POR RANK: os pesos LoRA já são sincronizados por broadcast explícito,
# então ranks com RNG diferente é o que queremos — senão as 4 GPUs sorteiam
# o mesmo sigma/ruído e o batch efetivo 32 tem só 8 σ distintos.
_set_seed(config.runtime.seed + accelerator.process_index)

Manter o smoke test (trainer.py:893) com a seed pura — é single-process e precisa ser reprodutível.

"metadata": {
    ...,

C9

concatenate_datasets sem alinhar colunas

baixo

genfocus_train/data.py:479-484

Por que é problema

concatenate_datasets exige features idênticas. Qualquer coluna a mais ou a menos entre os dois repos levanta exceção — e isso acontece depois do filtro de nitidez, que leva ~20 min. Carregar image_pre_deblur (não usado) ainda desperdiça I/O.

Como tem que ficar

_DEBLUR_KEEP = ["image_blur", "image_focus", "file_name_base"]

def _load_hf_sources(sources):
    loaded = []
    for source in sources:
        ds = _load_hf_split(source)
        faltando = [c for c in _DEBLUR_KEEP if c not in ds.column_names]
        if faltando:
            raise ValueError(f"{source.name}:{source.split} não tem {faltando}")
        # Alinha o schema ANTES do concat: o concatenate_datasets exige features
        # idênticas e falharia só depois dos ~20 min do filtro de nitidez.
        # image_pre_deblur é descartado de propósito (variante §3.4, não usada).
        loaded.append(ds.select_columns(_DEBLUR_KEEP))
    return loaded[0] if len(loaded) == 1 else concatenate_datasets(loaded)

Fazer o select_columns dentro de _load_hf_split, antes do _select_top_k_sharpest, para o filtro também ficar mais leve.

C10

Nenhuma validação durante o treino

médio

genfocus_train/trainer.py · loop principal

Por que é problema

state.best_loss é a loss de treino de um único micro-batch, com σ e ruído sorteados — não é sinal de nada. Não há avaliação em split de validação em 60K steps, e keep_last_n_checkpoints=5 descarta checkpoints por ordem, não por qualidade.

Como tem que ficar

A cada eval_every_steps (novo campo em RuntimeConfig, sugestão 1000), rodar o mesmo forward de treino sobre N amostras fixas de akcit-pixel/DDPD:validation (73 imagens), com σ e ruído fixos por seed — assim a métrica é comparável entre steps:

# σ determinístico: uma grade fixa cobrindo o range, mesma para todo step.
sigmas_val = torch.linspace(0.1, 0.9, 9)
gen = torch.Generator(device=device).manual_seed(1234)

Logar deblur/val_loss e usar essa métrica para best_loss e para decidir qual checkpoint preservar. Não tentar rodar as 28 etapas de denoise + LPIPS dentro do treino — caro demais e desnecessário para seleção de checkpoint.

C11-1 · Resolução armazenada (bloqueante para a Tabela 2)

Depende do C0-1. Se o akcit-pixel/DDPD estiver gravado em ~1024×688 em vez do original 1680×1120, o df já reduziu o blur em 1,64× em relação aos dados do paper, e as nossas métricas são calculadas sobre imagens reduzidas — não são diretamente comparáveis aos números publicados. Registrar em PANORAMA.md com a ressalva explícita e, se possível, regerar os dfs na resolução original.

C11-2 · Escala inconsistente entre fontes

Com “lado menor → 512”, um DDPD 1024×688 encolhe 0,744× e um RealBokeh_3MP (~2048×1536) encolhe 0,333×. As duas fontes entregam blur em regimes espaciais diferentes dentro do mesmo treino. A Opção A do C4 elimina isso automaticamente; com a Opção B, é obrigatório normalizar antes.

C11-3 · DPDD com 344 linhas, não 350

O split oficial é 350/74/76 (500 cenas); o repo tem 344/73/75 = 492. O paper diz “all images from the official training split”. Verificar se a perda foi intencional e documentar.

C11-4 · Balanceamento DPDD vs RealBokeh

344 + 3000 com shuffle uniforme → DPDD é 10,3% das amostras, e DPDD é a mesa da Tabela 2. O paper não especifica peso. Adicionar sampling_weight opcional em DatasetSourceConfig e medir junto do experimento do C4 — não mudar às cegas.

Conferido e correto — não mexer

Reauditado contra Inference_deblurNet.py, demo.py e Genfocus/pipeline/flux.py.

  • Ordem dos branches [texto, main, *cond] e o assert len(adapters) == len(timesteps).
  • Timesteps por branch [σ, σ, 0] — a condição é “limpa” (flux.py:621).
  • Guidance da condição = 1.0 (flux.py:622) — bate com o treino.
  • IDs de posição: position_delta=[0,0], position_scale=1.0; o treino usa _prepare_latent_image_ids(B, H//2, W//2), idêntico ao fallback do encode_images.
  • group_mask: com 1 condição, ones e ones + diag(1) são o mesmo tensor.
  • Prompt "a sharp photo with everything in focus".
  • Alvo do flow: x_t = (1-σ)x₀ + σε, v* = ε - x₀ — bate com o FlowMatchEulerDiscreteScheduler.step.
  • Normalização [-1,1] via /127.5 - 1 == image_processor.preprocess.
  • alpha = r → scaling = 1, que é o valor que specify_lora força na inferência.
  • Export .safetensors em fp32 — o load_state_dict do PEFT converte no load.
  • AcceleratedOptimizer.step()/zero_grad() são guardados por sync_gradients; chamá-los fora do if não duplica updates.
  • 28 etapas de denoise, TILE_SIZE=32 (512 px), overlap 4 (64 px), blend gaussiano — nada disso é decidido no treino.
  • image_pre_deblur não usado: correto, é a variante §3.4, que na inferência usa position_delta=[0, 32] na condição extra.
